# Hands-on results: 03 Input and output modules + gap list item 12 (GL-144)  (agent H3, 2026-10-07)

Every check ran the real program in its own process, off-screen
(`QT_QPA_PLATFORM=offscreen`, Windows fonts), with a temp USERPROFILE under
`.agent-logs/handson/H3/home-*`, `GREMLIN_OFFLINE=1`, the hang tool on, and
`test/fake_hardware.py` (a "pJoy Pro" stick, vJoy 1). Nothing ran on the real
screen; no OS-level input was sent; the user's data, HidHide, vJoy and ViGEm
were not touched. The program was driven in-process: card signals (what the
card menu items send), `Commands.trigger(...)` (the Tools / File menu
commands), QTest mouse and key events on the program's own windows, raw
driver events through the fake dill callback, and key events through the
keyboard hook's callback list. Probes: `.agent-logs/handson/H3/probe_*.py`
(run by `run_probe.py`); each run's full result is
`.agent-logs/handson/H3/<probe>-<part>.json`. Screenshots were all looked at.

## Failures (one paragraph each: row, spec ref, what happened, file:line of the likely cause, suggested fix)

**S40 (03 S40, tracker A1).** With unsaved ticks in Module Setup for pJoy Pro, choosing Module Setup for vJoy 1 asks Save / Discard / Cancel as it should, but after Discard (or Save) only the first window closes: vJoy 1's window is not opened, so the user has to choose Module Setup again. Spec: "close the first (asking about unsaved changes) and open a fresh one". Cause: `qml/Main.qml:542-547`. `openConfigureModule` calls `old.close()`, sees it still open because it is asking, and returns. The request for the other device is dropped. Fix: keep the pending (direction, card) and open it from the old window's `closing` once the close is accepted (Discard, or Save then close). Cancel should drop it.

**S78 / D-03-Q8-NOFILE (found while checking S73).** A card for a device with no module file (pJoy Pro and vJoy 1 at first start, and pJoy Pro after Delete Device) shows no counts line. The model carries the device's own counts (64 / 6 / 2, as `test_final_03::test_s72_...` asserts), but `qml/StatusCard.qml:185` hides the line with `visible: isModule`. Decision D-03-Q8-NOFILE: "A Home card for a device with no module file shows the device's own counts". Fix: show the counts line on no-file cards as well (or `visible: isModule || isStub`), and keep Keyboard / OSC / Xbox, which have 0 / 0 / 0, as they are.

**S101 (03 S101).** Calibration opened for a stick that isn't plugged in (initialSlug "second_stick") shows the first connected stick (pJoy Pro) and keeps showing it after Second Stick is plugged in; `waitingSlug` stays "second_stick". The card menu itself opens on the right stick when it is connected. Cause: `qml/DialogCalibration.qml:72-80`: `chooseModule` sets `waitingSlug` and returns with `shownSlug` empty. Then the ComboBox's `onCurrentValueChanged` / `onCountChanged` (`:195-206`) fills `shownSlug` with the first stick. The `onModelReset` handler (`:152-160`) switches to the waiting device only when `shownSlug` is not in the list, which never happens here. Fix: while `waitingSlug` is set, don't auto-pick the first stick (show "This input module is not connected." for the waiting one). Or, in `onModelReset`, switch to the waiting slug when it appears and nothing unsaved is shown.

**S114 (03 S114, tracker N11), corner case.** With Calibration open, Run then Stop turns input highlighting back on: `suspend_input_highlighting()` is False and stick presses highlight on the Configuration page while Calibration is still open. Cause: `gremlin/ui/backend.py:470-475`. `activate_gremlin`'s `finally` calls `set_suspend_input_highlighting(False)` whenever the runner is stopped, without checking `_highlight_holders` (which holds "calibration"). Fix: in that `finally`, resume only when `self._highlight_holders` is empty, the same check `resumeInputHighlighting` makes.

## Needs a person (what exactly to do and what to look for)

- **S26:** with a Keyboard module that claims only F and a profile with an action on F, press Run. Type in Notepad, then in a game's chat box. Every key should arrive in both, and only F should fire its action. A program can't check this: it needs real typing into other programs.
- **S41 (CFGM-02b):** with a real stick, open Input Module Setup and press a button far down the list. Its row should tick, light green and scroll into view. In Output Module Setup the text should only say "Tick the outputs…". The program-driven check passed with fake hardware.
- **Batch 1 (GL-075/076/090):** with your real sticks plugged in, start the program on Home. `system.log` should have no line "Module file of … looked up without its device id". This passed with fake hardware.
- **Batch 3 (C3a), real vJoy:** View › Profile Settings should list each vJoy device that has an output module (vJoy Behavior, vJoy Initial Values). This passed with fake vJoy queries.
- **Batch 3 (C3a), keep-alive:** Run a profile that writes vJoy 1 once, then leave it idle for more than 2 minutes. vJoy 1 should stay acquired by Gremlin (vJoy Monitor or Joy.cpl still sees it). After Stop it should be released, with no further resets. This passed with an in-memory vJoy driver and a 1.5 s interval.
- **S115, real vJoy (optional):** Output View of vJoy 1 should be still while stopped. With Run on, press a mapped stick button: the matching tile should light. This passed with the stand-in driver.

## Notes (not failures of these rows; for the lead)

- Probe artefact, not a program fault: driving the program with `QTest.qWait` holds the Python GIL, so the "device list update" thread took about 27 s to handle a plug-in. With an event pump that sleeps between passes, as `app.exec()` does, it took 0.25 s. The probes use the sleeping pump.
- Keyboard Module Setup shows the stick wording "Press a control on the device… 5-way hats are set in the Button Map" (`qml/DialogConfigureModule.qml:287-291`), which fits a keyboard poorly.
- S54's note for a renamed stick says "Import that file to copy it here". Since 03 Q13 an import goes into the file the device already uses (old_name.json), so this advice reads oddly. The lead may want to check the wording.
- At Run start the pJoy Pro card's last line showed "last: Axis 2" with nothing touched, probably the Run-start axis refresh (S74 / GL-244 area; not checked further).
