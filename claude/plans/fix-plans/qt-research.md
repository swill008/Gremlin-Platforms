## Q1 Windows plugin and external show
- QWindow::isVisible() returns the Qt-side requested flag `d->visible` (qwindow.cpp), NOT the HWND state. QWindowsWindow::isVisible() asks the OS (IsWindowVisible). So an outside ShowWindow(SW_SHOW) on a window Qt hid does not flip QWindow::isVisible() or visibility(). windowsProc has no WM_SHOWWINDOW case by name; only QtWindows::ShowEventOnParentRestoring (QTBUG-40696, suppresses re-showing hidden transient children). Unverified: the full message-to-event mapping in windowsEventType().
- visibility is computed in QWindowPrivate::updateVisibility(): !visible -> Hidden, WindowMinimized -> Minimized, etc.; emits visibilityChanged when it changes. A minimized window has isVisible()==True and visibility()==Minimized.
- Native minimize/restore path: WM_SIZE -> QtWindows::ResizeEvent -> QWindowsWindow::handleResized(SIZE_MINIMIZED/MAXIMIZED/RESTORED) -> handleWindowStateChange() -> QWindowSystemInterface::handleWindowStateChanged -> setWindowStates -> updateVisibility -> visibilityChanged. Guarded by WithinSetStyle/WithinSetGeometry flags (no event then). So taskbar SC_RESTORE on a Qt-visible minimized window does update visibility. On minimize handleWindowStateChange also calls handleHidden() -> fireExpose(empty region), i.e. unexposed.
- Hidden-by-Qt then shown by others: expected out-of-step (Qt flag False, HWND visible). WM_PAINT -> handleWmPaint -> fireExpose(force) would still raise exposeEvent/isExposed (inferred, unverified). Expose is the best hook for "actually on screen": doc says isExposed() = exposed in the windowing system, can differ from isVisible(); exposeEvent fires on each change; resize precedes first expose.
- WM_DISPLAYCHANGE / settings: QtWindows::SettingChangedEvent -> m_screenManager.handleScreenChanges(). WM_DPICHANGED: DpiChangedEvent -> handleDpiChanged. Power: qWindowsPowerWindowProc only InvalidateRect on visible non-minimized windows when display turns on. No code seen that shows/hides windows on those events.
- Known bugs (titles only from search, reports not opened; Jira moved to qt-project.atlassian.net and was not readable): QTBUG-124177 (Qt 6.5.3, Win11: hidden maximised window shown again after remote desktop reconnect gives blank native window while Qt side stays hidden; unresolved), QTBUG-38856 (external show/hide messages stop updates; closed out of scope), QTBUG-82059 (QWindowPrivate::setVisible emits visibleChanged before platform applied; recursion risk), QTBUG-63602 (parent/child visibility inconsistent). URLs: https://bugreports.qt.io/browse/QTBUG-124177 etc. Treat details as unverified.

## Q2 hide() inside visibilityChanged for Minimized
- No Qt doc or bug found about it. qwindow.html says only hide()==setVisible(false), hideEvent is the hide hook. Code reading: setVisible(false) from the handler runs during setWindowStates->updateVisibility (emit inside update), then updateVisibility is re-entered and visibility becomes Hidden: nested emission, so the handler sees Hidden while the outer emit is still unwinding (reasoning from qwindow.cpp, unverified by test). Also native: window was SW_MINIMIZEd then hidden; restoring later goes via setVisibility(last mode) as system_tray.py line 124 does. Safer pattern: QTimer.singleShot(0, window.hide) from the handler. Our handler is system_tray.py:243-267 (hide at line 267), restore at line 124.

## Q3 Worker thread (not verified by source, search found no measurements)
- No benchmark of PySide6 queued-signal cost found. Gap: needs our own micro-benchmark. Qt queued call = allocate event + post; PySide additionally acquires the GIL to marshal Python args in the receiving slot (inferred).
- Pattern: QObject worker + moveToThread + QThread.start(); timers created in the worker (or in a slot run on it) run on its event loop; a Python slot decorated with @Slot runs in the receiver's thread only when the connection is queued/auto across threads. Forum thread https://forum.qt.io/post/819201 reports a PySide6 slot running in the signal's thread despite Auto/Queued (cause not verified; typical cause is a non-@Slot callable/lambda lacking a thread context). Prefer @Slot methods on the QObject.
- GIL: pure-Python worker and GUI thread share one GIL (switch interval default 5 ms); I/O waits and most Qt C++ calls release it. A busy input thread can add latency to GUI slots; blocking calls (ctypes/pywin32 waits) release it. QTimer drift on a busy loop: https://www.pythonguis.com/faq/qtimer-expectations/.
- Free-threaded: Qt for Python 6.9 blog says early tests "very promising" (https://qt.io/blog/qt-for-python-release-6.9); no support declaration found; unverified for 6.11. PyQt also undeclared.
